## Problem Statement
AI coding/research agents need good evidence, not links. User's words: "quality of web search is also a major concern. good info yields good results", and "can you build sth on par with the paid tier?". Paid agent search (Parallel, Exa) is the bar. Cost must be controlled, and routing must be automatic: "cant ask me to decide for each query", "the decision model can be swapped, not hardcoded".

## What Makes This Cool
Most of these queries have known, authoritative homes with free structured APIs: docs.rs/official docs, GitHub issues/releases/code, Stack Exchange, package registries, arXiv/OpenAlex/Semantic Scholar/PubMed, SEC EDGAR. They return exact versions, dates and accepted answers as data. A router that sends each query to the right home, with SearXNG for the long tail and paid search only when a measured trigger fires, could beat general neural indexes on version/date accuracy without building an index. **Hypothesis, unmeasured.** M1 exists to test it.

## Constraints (agreed this session)
- **References:** Parallel and Exa (SEARCH-09).
- **Workload (all graded):** version-specific library/API docs; exact errors and troubleshooting; recent releases/changes; broader technical research; scientific research; market research.
- **Done bar:** statistically tied overall with the best reference at lower total cost. "Tied" means **demonstrated equivalence**: the confidence interval of the per-query quality difference lies within a user-approved equivalence margin, with the sample size justified by a power calculation. Failing to detect a difference is not a tie; an underpowered result is reported as **inconclusive**. M1 comparisons are exploratory; only the final acceptance run can claim parity. Grading is blind; per-category results are reported so a weak category is visible.
- **Latency:** two modes chosen automatically: quick ~5-10 s, deep ≤1-2 min.
- **Runtime:** local first on this Windows 11 ARM64 PC via Docker Compose (Docker 28.4, WSL2 Ubuntu present); packaged so a VPS move is config-only.
- **Budget:** not $0 (Jev already in use). The monthly cap is set after M1 measures what each paid component buys. M1 live reference/eval spend needs its own separately approved cap. Reference point: one recorded Jev call cost ~$0.000029 for 687 input tokens (single measurement; recheck pricing).
- **Rust-first.** cargo is not installed on the Windows side, so installing a toolchain needs approval.
- No tests call live APIs; live checks are separately approved and capped.

## Premises (user agreed all six)
1. MCP server (stdio for Pi/local agents, optional HTTP) returning a cited evidence package: passages, URLs, dates, versions, contradictions, gaps. Quick/deep mode chosen by code (SEARCH-03/04).
2. Discovery is a routed hybrid with no own global index: vertical connectors, self-hosted SearXNG, and trigger-gated capped Exa/Parallel fallback (SEARCH-01/06).
3. Jev (swappable) does bounded semantic judgments: relevance/version fit, passage selection, coverage gaps. Deterministic code owns limits, deadlines, cache, budget and a no-classifier fallback path. No silent paid fallback (SEARCH-05).
4. Evaluation early (M1): a frozen query set across all categories, blind-graded against Parallel and Exa (SEARCH-09/06).
5. Rust core. SearXNG stays an upstream Python container. Extraction (Trafilatura vs a Rust readability crate) and local reranking (ONNX via Rust) are chosen by measurement and recorded in Decisions.md (SEARCH-08).
6. Local Docker on this PC (arm64 images), deployable anywhere; publishing deferred until approved (SEARCH-07/08).

## Approaches Considered
- **A) Extend mcp-searxng/Kindly plus a Rust sidecar.** Rejected: two runtimes and MCP layers split caching, cancellation and cost accounting; weak Rust-first exception.
- **B) Rust-native evidence engine, eval-first.** Chosen.
- **C) Paid-first strangler.** Rejected for now: paid spend before a cap exists. Its idea of per-category paid-vs-free measurement is kept inside B's eval.

## Recommended Approach: B
One Rust service (tokio; official `rmcp` MCP SDK, verify at implementation time).
- **Controller:** classifies the query (category, version/date sensitivity), picks quick or deep mode, and owns deadlines, cancellation, concurrency limits, retries and per-query and monthly budgets.
- **Retriever trait:** SearXNG, GitHub, Stack Exchange, registries/docs.rs/official docs, arXiv/OpenAlex/Semantic Scholar/PubMed, SEC EDGAR and other market sources (to be chosen), plus Exa and Parallel as capped fallbacks behind explicit triggers (low relevant-source count, a coverage gap, a semantic-similarity need, upstream throttling). Paid escalation is possible only when preapproved configuration enables it and budget remains. It requires no per-query user decision. Every escalation is disclosed in the returned evidence metadata (provider, trigger, actual or estimated cost) and recorded in the ledger.
- **Fetch/Extractor trait:** safe URL handling (scheme/host allowlist, SSRF guard, size/time limits, robots behavior to decide), HTML-to-text, code-block preservation, date/version metadata.
- **Judge trait:** Jev via OpenRouter, a local ONNX cross-encoder, or a heuristic, selected by config. Bounded call count and tokens. On failure or budget exhaustion it falls back to the heuristic and says so in the output.
- **Evidence packager:** compact passages with citation, date, version, qualifiers, contradictions and an explicit coverage-gap section.
- **Storage:** SQLite for the cache (URL/content/query) and a cost ledger (tokens, API fees, latency per stage).

## Contracts and gates (fixed before implementation)
- **Result semantics.** Each stage reports `ok | failed | timeout | skipped(budget) | skipped(policy) | cancelled`. Response status, in precedence order: `failed` if no usable evidence exists (error class: `deadline`, `budget`, `upstream`, `policy`, `cancelled` or `internal`, plus all stage outcomes); otherwise `complete` only if every required planned stage ended `ok`; otherwise `partial` (usable evidence returned, with non-`ok` stages listed). "Not found" for a subquestion may be claimed only when every search relevant to it ended `ok` with no matching evidence. A search that failed, timed out, was skipped or was cancelled never supports a negative conclusion; its gap is reported as *unsearched*. When the deadline expires, the response is `partial` if usable evidence exists, otherwise `failed` with error class `deadline`. Mocked tests cover a successful empty search vs a connector failure, and a deadline before vs after the first usable evidence.
- **Cancellation and paid liabilities.** On caller cancellation the controller stops new dispatches immediately, cleans up local tasks and attempts upstream cancellation where the provider supports it. Before any paid call (Exa, Parallel, OpenRouter/Jev) the controller reserves its maximum expected cost against the shared budget; dispatch is refused if the reservation would exceed the cap. After completion or cancellation the reservation is reconciled against the actual charge (or kept as an estimate until reported). In-flight charges therefore cannot exceed the cap or disappear from the ledger. Charges that couldn't be avoided after cancellation are disclosed in the ledger and, where a response is still returned, in its metadata. Mocked tests cover cancellation with delayed charge settlement and concurrent reservations at the cap.
- **Cache freshness.** Cache keys include the normalized query, mode, category, version pin and config hash. Version-pinned docs/content: long TTL, revalidated with ETag/Last-Modified. "Latest", release and date-sensitive queries: short TTL, plus revalidation before reuse. Stale-on-error is allowed only when flagged. Evidence carries `retrieved_at` and `stale: true|false`. Regression tests cover a version bump invalidating a cached answer and stale reuse being flagged.
- **Untrusted content boundary.** Fetched text is data, never instructions. It never changes controller policy, budgets, tool calls or URLs to fetch, except links that pass the same URL policy. Judge outputs are schema-validated values (choices/scores) consumed by bounded code; invalid output goes to the heuristic path. MCP evidence marks source text as untrusted quoted content. Adversarial fixtures cover instruction-override and credential-exfiltration attempts embedded in pages.
- **Source access policy gate.** No source receives live automated traffic until its access method (official API vs fetch), ToS/robots treatment, rate limit, backoff and throttling behavior are documented in Sources.md and enforced in code (per-host rate limiter, bounded retries with jitter, honoring Retry-After).
- **Comparison protocol (prerequisite to any baseline run, user-approved):** the exact Parallel/Exa products, endpoints, modes and settings; identical query inputs; the same output contract (evidence passages plus citations) for all systems; a common rubric (must-have facts, citation support, version/date accuracy, qualifiers, contradictions, unsupported claims) with failures scored as zero; blinded, shuffled packets with system identity stripped; and system/version/config recorded with each run.
- **Cost protocol (user-approved):** the same workload and quick/deep mix, cold and warm cache reported separately, all paid calls and retries counted. **Operating cost** (the per-query total used for the "lower total cost" claim) includes online routing/relevance/passage-judging API fees, tokens and retries, and local inference runtime. **Evaluation-only cost** (grading-judge calls, reference/baseline runs) is reported separately and excluded from the per-query total. The protocol also states: downstream model-input tokens from evidence size, priced at a stated model rate; self-hosted runtime allocated at a stated fixed monthly amount over a stated query volume, and pricing dates recorded. M1 evaluation spend is kept separate from operating cost.
- **M1 validation matrix (mocked, offline):** connector failure, timeout and malformed responses; deadline and cancellation cleanup (no leaked tasks); concurrent requests exhausting a shared budget (no overspend); upstream 429/Retry-After handling; URL policy for blocked schemes, private/loopback/link-local IPs, redirects to blocked targets and DNS rebinding (resolve-then-pin); cache freshness cases above; injection fixtures; and judge failure falling back to the heuristic. Load and soak tests, VPS deployment checks and observability dashboards are deferred M3/M4 obligations (no detailed inventory exists yet) and are not claimed in M1.
- **Eval harness (Rust crate):** frozen query set, recorded fixtures for offline tests, a capped live runner for references, blind grading packets (judge model plus user spot checks), and a significance test for "tied".

### R2-1 — clarity (blocking)

**Problem**

> mattC-main-design-20261011-105126.md:50 defines complete as 'all planned stages ran' and allows 'Not found' when every planned stage 'completed', rather than requiring successful searches. A failed connector has also run and completed. These conditions overlap the partial definition and do not conclusively prevent unsuccessful searches from being reported as verified absence. This part of R1-4 remains unmet.

**Remedy**

> Require successful completion of the required planned stages for complete and successful execution of the relevant searches before any 'Not found' claim. Explicitly exclude failed, timed-out, and skipped searches from negative-search conclusions. Define status precedence and add mocked assertions distinguishing successful empty searches from connector failures.

### R2-2 — consistency (blocking)

**Problem**

> mattC-main-design-20261011-105126.md:50 unconditionally returns partial on a deadline, but the same line requires usable evidence for partial and defines failed as no usable evidence. A deadline before the first usable passage therefore has two contradictory outcomes. This is a new contradiction in the added deadline rule.

**Remedy**

> Specify that deadline expiration returns partial only when usable evidence exists; otherwise return failed with a deadline/timeout error class and stage outcomes. Add separate offline tests for deadlines before and after usable evidence is collected.

### R2-3 — feasibility (blocking)

**Problem**

> mattC-main-design-20261011-105126.md:50 promises no billable expenditure beyond that already spent at cancellation. Cancelling local tasks does not establish that an already-dispatched Exa, Parallel, or OpenRouter request stops remotely or cannot incur subsequently reported usage charges. The design does not distinguish cancellable local work from irreversible provider liabilities, leaving this guarantee unsupported and its interaction with the shared budget unclear.

**Remedy**

> Promise immediate cessation of new dispatches and cleanup of local work, with best-effort upstream cancellation where supported. Define how in-flight paid liabilities are reserved before dispatch and reconciled after cancellation so they cannot exceed the cap or disappear from the ledger. Disclose unavoidable charges and test cancellation with delayed provider charge settlement using mocks.
